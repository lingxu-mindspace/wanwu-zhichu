## 2. 逐项结果

### 2.1 v1 部位伤害判定（实测原型）

**测什么**：服务端权威的 2D 扫掠碰撞，武器线段在帧起止位置之间插值 8 个子步，与 10 个身体部位（圆/矩形/线段）求交；命中后按部位倍率和护甲减伤结算。

**怎么测**：本地起 HTTP+WS 服务，两个客户端，攻击方固定 50 次挥砍，目标在身体上随机偏移；模拟 0/10/50/150/300 ms 网络延迟各一轮 [S]，每轮统计命中数与 RTT。

**结果**（`results/2026-11-07/v1-hit-location.txt`）[S]：

| 模拟延迟 | 命中 | 平均 RTT [S] | 服务端判定耗时 [S] |
|---|---|---|---|
| 0 ms | 50/50 (100%) | 5 ms | 0.220 ms |
| 10 ms | 50/50 (100%) | 16 ms | 0.120 ms |
| 50 ms | 50/50 (100%) | 58 ms | 0.100 ms |
| 150 ms | 50/50 (100%) | 158 ms | 0.080 ms |
| 300 ms | 50/50 (100%) | 313 ms | 0.120 ms |

**怎么读**：RTT 与配置延迟基本对齐（差值来自 WS 往返与 10 ms 发送间隔）；判定全部在服务端完成，耗时 0.08–0.22 ms [S]。**100% 命中是构造出来的**：挥砍方向瞄准了身体，子步数 8，几何上必然相交。它证明的是"判定链路能贯通"，不是"实战命中率"。

**已知缺陷**：
- `packetLossRate` 配置存在但从未被读取，所有轮次实际为 0 丢包。
- 伤害曾重复乘系数（部位倍率已 ×30，又乘武器基础伤害 30，合计 ×900），本次已修复为只乘一次，见 §4.4。命中/RTT 不受影响。
- 客户端 2 个文件、共享类型 2 个文件在迁移中损坏为全零，无法恢复；本仓库只保留服务端与自动化测试。

### 2.2 v2 天道事件流 + 链式哈希日志（实测原型）

**测什么**：按权重生成 7 类事件（含 5% 封神检测），按名义速率节流；日志模式下每条事件写入 SHA-256 链（`prevHash` + 时间戳 + id + 数据），事后从头部重算整条链。

**结果** [S]：

| 场景 | 实际吞吐 [S] | 事件数 | 链校验 [S] |
|---|---|---|---|
| 1K/s × 3s | 906/s | 2,800 | — |
| 10K/s × 3s | 6,341/s | 19,100 | — |
| 50K/s × 3s | 6,412/s | 19,300 | — |
| 100K/s × 3s | 63,413/s | 191,000 | — |
| 10K/s × 10s + 日志 | 6,340/s | 63,400 | 63,400 条 / 71 ms |
| 200K/s × 3s + 日志 | 73,163/s | 220,000 | 220,000 条 / 223 ms |

**怎么读**：
- 链校验速度约 1 M 条/秒（71 ms / 63,400；223 ms / 220,000）[S]，重算全链未发现断链。
- **吞吐不是容量上限**：50K/100K/200K 场景实测只有 6.4K/63K/73K 条/秒，因为每批之后 `setTimeout` 等待，而该环境的事件循环定时器下限约 15.6 ms [A]；名义 100K/s 根本发不出来。本次没有做无节流压测，因此**不知道容量上限**。
- 日志只在内存里，验证的是"链式结构能算对"，不是持久化、不是外锚定、不是防篡改存储。

### 2.3 v4 全球化地图流式（模型推演 + 真实内存分配）

**测什么**：40×40 区块、每区块 1–12 MB 的模拟数据，按玩家位置维护加载/卸载队列，逐帧处理。玩家沿路径移动，统计帧时间、卡顿次数、常驻内存、跨界次数。

**结果** [S]/[A]：

| 场景 | 平均帧时间 | 最大帧时间 | 卡顿(>33ms) | 内存 | 跨界 |
|---|---|---|---|---|---|
| 步行 1 人 | 17.8 ms [A] | 39.9 ms [A] | 15 | 246 MB [S] | 0 |
| 骑马 1 人 | 17.9 ms [A] | 41.2 ms [A] | 11 | 252 MB [S] | 1 |
| 50 人跨界 | 18.3 ms [A] | 42.3 ms [A] | 9 | 379 MB [S] | 73 |
| 100 人主城 | 20.2 ms [A] | 42.0 ms [A] | 19 | 1,152 MB [S] | 13 |

**怎么读（重要）**：帧时间不是实测渲染帧率。代码里 `ft = 16 + 0.3 × 加载耗时 + 随机 2 ms + 本帧真实耗时`，其中"加载耗时"本身也是 `数据量 × 5 ms + 随机 20 ms` 的模型值，没有真实磁盘 I/O。[A] 真实的只有 `Buffer.alloc` 的内存占用和每帧队列/遍历等逻辑开销 [S]。

因此 v4 的结论应表述为：**分块管理器与加载/卸载队列的组织方式可运行，模型口径下帧时间在 16.7 ms 量级 [A]，100 人主城场景常驻内存超过 1 GB [S]**。它不能说明真实引擎的帧率、磁盘吞吐或网络加载表现。100 人场景的 1.15 GB 全部是真实分配的缓冲区，靠 GC 不一定能及时回收，实际实现需要预算与上限。

### 2.4 v5 NPC 社交与记忆（实测原型）

**测什么**：生成 N 个 NPC，每个约 500 条记忆（上限 1,000，按重要性截断），30 天前的低重要性记忆衰减；测 10,000 次 NPC 本地记忆查询，以及按玩家 ID 的全表扫描。

**结果**（`NPC_COUNT=10000`）[S]：

- 生成：10,000 NPC / 4,996,290 条记忆 / 491,831 条社交边，耗时 2,252 ms [S]。
- 本地查询：avg 0.0112 ms，p95 0.0157 ms，p99 0.0215 ms。
- 衰减：30 天后衰减 1,224,523 条（24.5%），剩余 3,771,767 条。
- 按玩家全表扫描：`player_42` 找到 408 条，耗时 125.05 ms。

**怎么读**：NPC 自己的记忆是数组 + `filter`，查询是 O(该 NPC 的记忆数)，所以亚毫秒；**跨 NPC 查某个玩家的全部记忆是 O(全部记忆)**，125 ms 在 5M 条时已经不可接受 [S]，真实实现必须建反向索引。生成过程是同步的，5M 条记忆占用的内存未单独测量。

### 2.5 v6 多人残像同步（数值仿真）

**测什么**：服务端产生 30 fps 时间轴，客户端按周期向服务端校正；客户端时钟带随机 ppm 漂移（并随延迟增大）。统计校正时的平均/最大误差，以及客户端之间的最大分歧。

**结果** [S]（仿真）：
| 场景 | 平均漂移 | 最大漂移 | 客户端间最大分歧 |
|---|---|---|---|
| LAN 5 人，1 s 同步 | 2.23 ms | 16.01 ms | 0.01 ms |
| 混合 8 人，1 s 同步 | 1.44 ms | 16.02 ms | 0.01 ms |
| 4 人，500 ms 同步 | 1.06 ms | 16.01 ms | 0.00 ms |
| 50 观看者，2 s 同步 | 4.99 ms | 16.04 ms | 0.01 ms |

**怎么读**：漂移最大 16.04 ms，恰好是一个 16 ms tick 步长 [S]，说明校正发生在采样边界附近，误差不会累积成一个周期以上。**这是纯数值仿真**：没有真实网络、丢包、乱序、时钟漂移或渲染延迟。它验证的是校正公式的行为，不是线上同步质量。

### 2.6 v7 动态技能池战斗 AI（实测原型）

**测什么**：效用函数选技能（阶段、距离、敌方状态、冷却、重复惩罚），随机噪声 ±15；测不同技能池大小下的单次决策耗时与"被用到的技能比例"，以及多 Boss 并发。

**结果** [S]：

| 技能池 | 平均决策 [S] | p95 [S] | 用到的技能比例 |
|---|---|---|---|
| 10 | 0.0012 ms | 0.0022 ms | 100% |
| 30 | 0.0015 ms | 0.0028 ms | 100% |
| 50 | 0.0023 ms | 0.0069 ms | 100% |
| 100 | 0.0028 ms | 0.0049 ms | 100% |
| 200 | 0.0071 ms | 0.0090 ms | 91% |
| 500 | 0.0195 ms | 0.0227 ms | 62% |

并发 Boss（100 技能池）：1/5/10/20/50 个 Boss 的平均决策为 0.0019/0.0021/0.0021/0.0020/0.0019 ms [S]。

**怎么读**：决策是线性扫池，500 技能仍只有 0.02 ms，远低于 16 ms 帧预算 [S]。"用到的技能比例"不是行为多样性：500 次决策、每次上冷却，最多用到 310 个不同技能（62%），这个指标受采样次数和冷却限制，不能当作"AI 行为丰富"的证据。

### 2.7 v8 全链路集成（集成原型）

**测什么**：100 玩家 + 20 NPC + 2 半神，2400 tick；战斗→功过→链式日志→封神检测→半神 AI→残像→NPC 社交串起来，跑 8 条检查。

**结果** [S]：

- 8/8 检查通过，0 失败 [S]。
- 2,003 次攻击，100% 命中（同样是瞄准构造）；1,454 次玩家死亡（含重生），1 名半神阵亡。
- 功绩 169,940 / 过失 30,358，封神检测 11 次，候选人 42，合格 0。
- 链式日志 3,569 条，平均写入 0.001 ms。
- 平均 tick 0.02 ms，最差 tick 2.00 ms，峰值内存 13.25 MB。
- 2400 tick 总耗时 0.1 s，报告"目标 120 s、实时比 0.00x"。

**怎么读**：
- 链路确实贯通了，最差 tick 2 ms 也远低于 20 tick/s 的 50 ms 预算 [S]。
- **没有实时节流**：循环不等 50 ms，直接跑完 2400 个 tick。所以"0.00x 实时比"不是吞吐能力，只是一句"测试没按实时跑"。
- "封神检测平均 0.00 ms""半神 AI 平均 0.0000 ms"低于毫秒计时器分辨率，**这两个数没有意义**。
- "合格 0 人"说明功过阈值一次都没被跨过；8/8 检查只验证"检测按周期执行了"，不验证"封神条件正确"。

## 4. 已修复的代码问题

### 4.1 v1 启动即崩溃

`Object.values(BodyPart)` 把 TypeScript 类型别名当运行时对象用，抛 `TypeError: Cannot convert undefined or null to object`。改为显式维护 10 个部位 ID 的数组。修复前 v1 一条结果都跑不出来。

### 4.2 v2 限速器失效

原实现 `wait = interval - 5`（固定扣 5 ms [D]），而循环实际耗时随批量大小变化，导致等待时间算错、名义速率不可达，首次复跑出现 9.7M/s 和 712K/s 的未节流假值。改为 `interval - 实际循环耗时`，并对负值取 0。修复后吞吐受定时器粒度限制，见 §2.2。

### 4.3 v5 默认规模与报告不一致

代码写死 1,000 NPC，报告写 10,000。改为读取 `NPC_COUNT` 环境变量，默认仍为 1,000；复跑用 10,000。

### 4.4 v1 伤害重复乘系数

`checkWeaponSweep` 返回的 `rawDamage` 已乘 30，`processAttack` 又乘 `weaponBaseDamage`（测试传入 30），实际伤害放大 900 倍。改为返回部位倍率本身，最终伤害 = 倍率 × 武器基础伤害。命中与 RTT 不受影响；修复后重跑 v1，结果与修复前一致。

### 4.5 损坏文件

迁移时扫描到 15 个全零字节文件：v1 的 5 个代码/结果文件、6 个验证目录的 `package-lock.json`、4 份重复的 v5 锁文件副本。锁文件删除后由 `npm install` 重新生成；v1 的代码文件无法恢复，已从本仓库移除并在 README 说明。

## 5. 方法与边界

**算证据的**：
- 本机实际运行原型得到的输出，含耗时、计数、内存占用。
- 链式哈希从头部重算全部通过。
- 集成测试 8 条检查的实际通过/失败。

**不算证据的**：
- 命中率：v1 / v8 的 100% 是瞄准构造，不代表实战。
- v4 帧时间：模型公式输出，不是渲染帧率。
- v6 同步质量：数值仿真，无真实网络。
- v8 吞吐：没有实时节流，也不代表生产承载。
- v2 吞吐上限：没有无节流压测，只知道"在该节流下能跑多少"。
- v7 "技能使用比例"：受采样次数与冷却限制，不是行为多样性。

**没有覆盖的**：
- 任何真实网络条件（丢包、乱序、抖动、NAT）。
- 持久化、崩溃恢复、日志落盘与外部锚定。
- 渲染、动画、物理引擎、UE5 实机。
- 安全、反作弊、并发一致性。
- 玩法、留存、可玩性。

这些是设计文档里明确留给制作阶段的内容，不应被这份报告暗示为已验证。
